Домашнее задание 9. Часть 1

Задача 1.1

1. Метод ProcessDamage принимает List<IDamageable>, чтобы не привязываться к конкретным классам вроде Player или Trap. С точки зрения полиморфизма это позволяет положить в один список вообще разные объекты и для каждого вызвать TakeDamage. При этом каждый объект отреагирует по-своему: у игрока отнимется здоровье, а ловушка сломается. Если бы метод принимал только List<Player>, пришлось бы писать отдельные методы под врагов, ловушки и каждый новый предмет.

2. Формально компилятор пропускает такой код, потому что все методы и свойства интерфейса в классе Trap написаны. Но по смыслу это нарушение контракта интерфейса, и для вызывающего кода такое поведение выглядит странно. Любой код при работе с IDamageable ждёт, что здоровье уменьшается, а false возвращается только когда объект уничтожен и HP дошло до нуля. У ловушки же HP всегда равно 10, но при любом ударе она сразу ломается, что путает логику проверки здоровья.

3. Если бы в GameSystem не было ProcessHeal и зелье попытались передать в ProcessDamage, программа бы даже не запустилась. Класс HealthPotion не реализует IDamageable, поэтому компилятор сразу выдаст ошибку несовместимости типов. Даже если бы мы попытались передать в TakeDamage отрицательный урон для лечения, ловушка бы всё равно сломалась, а проверка здоровья у игрока сработала бы неправильно. Разделение на два интерфейса как раз защищает программу от таких ошибок.

4. Придётся изменить классы Player и Trap, так как оба реализуют IDamageable, а вот HealthPotion трогать не нужно. Если не добавить свойство IsDead в эти два класса, код не скомпилируется и выдаст ошибку. В этом и суть контракта: интерфейс жёстко гарантирует, что у любого класса, который его реализует, точно есть все нужные свойства и методы.

1. Может содержать поля с конкретными значениями

Interface: -
Абстрактный класс может хранить обычные поля со значениями, а интерфейс описывает только поведение и не хранит состояние.

2. Может иметь полноценный конструктор
Abstract class: +
Interface: -
У абстрактного класса есть конструктор для создания наследников, а интерфейс создать напрямую нельзя, поэтому конструкторов у него нет.

Abstract class: +
Interface: +
Абстрактный класс всегда мог иметь обычные методы с телом, а в новых версиях C# в интерфейсах тоже разрешили писать методы с реализацией по умолчанию.

5. Может объявлять свойства без реализации
Abstract class: +
Interface: +
И в абстрактном классе, и в интерфейсе можно объявить свойство без реализации, которое обязаны написать наследники.

6. Может быть использован как тип поля или переменной

7. Может наследовать классы

Interface: +

Дополнительный вопрос к задаче 1.2

Общую основу персонажей лучше вынести в абстрактный класс Character, а отдельные способности оформить через интерфейсы.

Схема наследования:
- Интерфейс IDamageable для получения урона
- Интерфейс IInteractable для открытия диалогов
- Интерфейс IHealable для лечения
- Абстрактный класс Character : IDamageable с полями Name и HP
- Класс Player : Character, IInteractable, IHealable
- Класс Enemy : Character
- Класс NPC : Character, IInteractable

Почему выбран такой подход:
Абстрактный класс подходит, когда объекты по сути являются одним и тем же и имеют общие поля вроде имени и здоровья, чтобы не дублировать код. Интерфейсы же нужны для отдельных возможностей вроде лечения или диалогов, так как к одному классу можно подключить сразу несколько разных интерфейсов.
